# Lenkeng LKV422 HDMI Matrix — Integration Notes

**Status:** driver complete against the stub (`tests/stubs/lkv422_stub.py`); **not yet run against hardware.**
**Scope:** the RS-232 command set as implemented, the connection model, the wiring facts a maintainer needs, and the two questions §7.5 leaves for the bench.
**Applies to:** `LKV422Driver` (`proskenion/core/drivers/lkv422.py`), registered as `video_matrix/lkv422`.

This file does not repeat §7.5's text — see `docs/proskenion-spec-v3.1.html`, "§7.5 HDMI Matrix — Lenkeng LKV422", for the reasoning behind each of these decisions. What follows is what the code actually does and cites where.

---

## 1. Commands, as implemented

Source: `proskenion/core/drivers/lkv422.py:104` (the reply pattern), `:174–211` (`route`), `:212–221` (`read_routing`), `:223–244` (`_read_routing_locked`, the actual exchange).

| Command | Sent when | Code |
|---|---|---|
| `PA{n}R` (`n` = 1–4) | `route()` is given every output (§7.5 single-intent rule) | `lkv422.py:191–192` |
| `PS{o}{i}R` (`o` = 1–2, `i` = 1–4) | `route()` is given a subset of outputs, once per output | `lkv422.py:193–194` |
| `PAXXR` | every routing read: the 25 s health probe (`probe()`, `lkv422.py:158–170`), a switch's confirmation (`route()`, `lkv422.py:205`), and any direct caller of `read_routing()` | `lkv422.py:230` |

Reply parsing: `RESPONSE = re.compile(rb"OKP(\d)P(\d)|ERR")` (`lkv422.py:104`), matched with `.search()` against the whole accumulated buffer — not anchored — so a stray unread acknowledgement ahead of a real reply cannot break the match (see §4).

**Not implemented:** `PAPXPX` (the combined syntax), `Reset`, `Recover`, `BaudXX`. §7.5 explains why: `PAPXPX` is functionally covered by `PA{n}R`/`PS{o}{i}R`, and the maintenance commands are not used at runtime. The baud rate is fixed at 9600 (`lkv422.py:82`) for the reason §7.5 gives: a factory `Recover` returns the device to 9600, and a controller configured for 19200 would then silently lose communication at exactly the moment someone is troubleshooting.

**Manual cross-check.** The Lenkeng LKV422 user manual (from Lenkeng; not redistributed in the public repository), §3 "RS-232 control", was read for this task. It matches §7.5's quotes exactly — same commands, same `OKP{a}P{b}`/`ERR` return values, same 9600 8N1 — and is equally silent on line termination and switch acknowledgement. No discrepancy was found between the manual and the specification.

## 2. Serial settings

9600 baud, 8 data bits, 1 stop bit, no parity (`lkv422.py:80–86`, `TRANSPORT_DEFAULTS["serial"]`). Default device path `/dev/hdmi-matrix` (`lkv422.py:78`); the path is an ordinary `device_path` field on the serial transport (§5.5 — a driver never mentions a path itself), so pointing it at `COM3` for development on Windows needs no code change, only different stored configuration.

## 3. Connection model (§7.5)

`connect()` opens the serial port and, on a `ConfigurationError` from the transport, re-raises with the two commissioning-time causes named explicitly, and the path actually configured — not a hardcoded default, so a development machine's `COM7` is named, not `/dev/hdmi-matrix` (`lkv422.py:141–157`):

> "cannot open the HDMI matrix serial port (...). This is a configuration or permissions problem, not a wiring fault: either <configured path> does not exist (the cable is unplugged, or the udev rule did not match — §4.12) or the application user is not a member of the 'dialout' group."

`probe()` (`lkv422.py:158–167`) is the connection event, not `connect()`: it calls `read_routing()`, and a `MatrixError` there (no reply, or a malformed one) becomes `ProbeResult(False, ...)` with the wiring diagnosis:

> "no reply to PAXXR within 1 s — a wiring problem: TX and RX not crossed, no common ground, or a signalling-level mismatch (§7.5), not a configuration fault"

Both paths use the standard §5.3 backoff (`Driver.run()`, `proskenion/core/drivers/base.py`) — 5 s doubling to a 300 s cap, resetting only after a successful probe.

## 4. Confirmed switching and the unread acknowledgement

`route()` never reads after sending a switch command (§7.5: the client does not wait for an acknowledgement). If the device turns out to acknowledge, those bytes are left sitting in the transport until the next request. `_drain()` (`lkv422.py:315–327`) discards them immediately before that request is sent, so they cannot be read as part of the confirmation reply. Belt and braces: even without `_drain()`, `RESPONSE.search()` would still find a genuine `OKP{a}P{b}` anywhere in a buffer that happened to start with stray ack bytes — draining just keeps the buffer, and the reasoning about it, simple.

## 4a. One exchange on the wire at a time

`route()` runs concurrently with the base driver's own periodic health-probe task, and nothing else orders them. A `PAXXR` from the probe landing while a switch is settling is not hypothetical: `_drain()` (§4 above) will discard whatever is sitting unread the moment it is called, and on a shared serial line that can be the *other* exchange's own confirmation reply, in flight for a reason `_drain()` cannot see. Left unguarded, a good switch could be reported unconfirmed, or confirmed from routing state that was never actually requested.

`self._lock` (`lkv422.py:136`, an `asyncio.Lock` created per driver instance) is held for the whole of one exchange:

- `route()` holds it across the entire send–settle–verify sequence (`lkv422.py:195–203`), so no probe can run between the switch and its own confirmation.
- `read_routing()` holds it for its single query (`lkv422.py:220–221`).

Both funnel into `_read_routing_locked()` (`lkv422.py:223–244`), which assumes the lock is already held and does the actual `PAXXR` exchange. `route()` calls it directly, from inside the lock it is already holding, rather than through `read_routing()` — an `asyncio.Lock` is not reentrant, so acquiring it a second time from the same task would deadlock. `tests/unit/core/drivers/test_lkv422.py::test_a_concurrent_probe_cannot_land_during_a_switchs_settle` starts a route and a probe concurrently against the stub, with a slow reply and a long settle to force the overlap, and asserts nothing reaches the stub during the settle window; it fails reliably (verified by hand) with the lock removed.

## 5. Routing-poll listeners

`add_routing_listener(callback)` (`lkv422.py:264–286`) registers an `async def callback(new, previous)` awaited whenever the driver's known routing changes — from the 25 s poll or from a route the driver made itself, per the contract set for this task. It fires from inside `_read_routing_locked()`, which every path above goes through, so nothing polls the matrix twice for the same information.

**Why 25 s, not §11.1's literal 30 s.** `PROBE_INTERVAL` (`lkv422.py:117`) is 25 s: the base driver's loop sleeps *after* each probe rather than before it, so at a literal 30 s the worst-case time from a front-panel change to the interface — one interval, plus the poll's own `PAXXR` round trip, plus a switch that happens to be settling — lands just past §18's 30-second bound. 25 s restores the margin without touching anything but this one constant.

**A listener does not need to tell its own route apart from a front-panel one.** Both notifications carry the LKV422's own reported state. A caller that just awaited `route()` already knows the outcome from that call's return (or its raised `MatrixError`); the notification only repeats it. A front-panel or IR change is the only case where the notification is the sole source of truth. Applying `new` unconditionally is correct either way — the same reasoning §7.5's *Destinations* section gives for divergence detection ("Because PAXXR returns real device state, this detects out-of-band changes as well as its own").

## 6. Wiring and cable (§7.5, `docs/hardware/network_map.md`)

- **Signalling level measured 2026-09-11: −9.21 V, true RS-232** (`docs/hardware/network_map.md`). Cable ordered: FTDI USB-RS232-WE-1800-BT_0.0.
- **Crossover:** cable TXD → LKV422 Rx; cable RXD ← LKV422 Tx; GND common. Both ends labelled at commissioning (§7.5 *Termination*).
- **Device path:** `/dev/hdmi-matrix`, matched by the cable's FTDI serial number (§4.12). Cable serial and resolved `/dev/serial/by-id/...` path are still *to be recorded at commissioning* in `docs/hardware/network_map.md`.
- **Permissions:** the symlink is group `dialout`; the application user must be a member, or `connect()` reports it as shown in §3 above.

## 7. Open questions — for the bench (`tools/lkv422_probe.py`)

Both are exactly as §7.5 leaves them; nothing below is a guess dressed up as a finding.

### 7.1 Line termination

Whether a reply ends in CR, LF, CRLF, or nothing. Doesn't block the driver — `RESPONSE` matches on content, not on a terminator (`lkv422.py:104`, `_read_reply`, `lkv422.py:331–354`) — but worth recording for anyone reading a raw capture.

**Bench result, 23 September 2026 — answered, and it is none of the four.**
The reply is **prefixed** with `CR` and carries **no trailing terminator**:
`PAXXR` returns exactly `b"
OKP1P1"`, seven bytes, every time. Measured on the
real matrix over the FTDI `USB-RS232-WE-1800-BT`, three consecutive queries in
one session, each captured in its own two-second window, all identical, at
**206–216 ms** after the send.

Three consecutive captures is what makes this a prefix rather than a trailing
terminator seen late: a `CR` that ended the *previous* reply would be absent
from the first capture and present on the others. It is present on all three,
including the first after a buffer flush.

`tools/lkv422_probe.py` then caught the clearest evidence of all, by accident
of timing — one `PAXXR` reply arrived split across two reads:

```
<- + 169.0 ms  b'
'
<- + 179.5 ms  b'OKP1P1'
```

The `CR` is on the wire about 10 ms *before* the payload it precedes. Nothing
about that is compatible with it terminating the reply before.

**A limitation of the probe worth knowing:** its summary line reports
`Terminator: none`, which is true and incomplete — it inspects only the tail
of a reply and never mentions the prefix. Read its raw capture, not its
summary, when the question is the shape of a reply.

**This vindicates matching on content.** A reader waiting for a trailing `CR`
or `LF` waits forever — there is never one — and would time out on every
healthy exchange. `RESPONSE` looks for `OKP{a}P{b}` or `ERR` and stops there,
so the driver is correct against this device by design rather than by luck.
Worth leaving exactly as it is.

The 206–216 ms latency also sits comfortably inside the one second `PAXXR` is
given (`lkv422.py:126`), with about four times the margin.

### 7.2 Switch acknowledgement

Whether `PA{n}R` / `PS{o}{i}R` return anything. Doesn't block the driver either — `route()` never waits for one (§4 above) — but changes what a raw capture at commissioning should expect to see.

**Bench result, 23 September 2026 — they do acknowledge.** `PA2R` returned
`b"
OKP2P2"` after 179 ms: the same shape as a `PAXXR` reply, carrying the
**new** routing rather than a bare "ok". The subsequent `PAXXR` confirmed
`{'1': '2', '2': '2'}`, so the acknowledgement told the truth.

**The driver should keep ignoring it, and the reason is worth stating.**
`route()` settles and then confirms with `PAXXR` (§4). Now that an
acknowledgement is known to exist, that looks like a redundant round trip —
about 180 ms per switch — and it is tempting to drop it. Don't:

- The acknowledgement is what the matrix says it is *about to do*; `PAXXR` is
  what it reports it *has done*. Only the second detects a switch that was
  accepted and did not take effect.
- §7.5's *Destinations* reasoning applies unchanged: because `PAXXR` returns
  real device state, confirming with it also catches out-of-band changes —
  front panel, IR — that an acknowledgement to our own command cannot.
- 180 ms on a matrix switch is not a cost anyone in the room can perceive,
  and this is the one exchange where being sure matters.

**The switch was witnessed, not just reported.** Simon watched the front
panel through the run: both output LEDs moved from input 1 to input 2 and
back. That matters more than it sounds. Everything else in this session is the
matrix describing itself over a serial line — an acknowledgement, and a query
agreeing with it, are both the device's own account. The LEDs are the only
independent evidence that the commands moved hardware rather than merely
being well-formed and politely answered. The whole chain is now proven end to
end: command, wiring, physical switch, acknowledgement, confirmation, restore.

What the acknowledgement does change is what a raw capture should look like:
a switch is **two** replies, not one, and a reader that assumed silence after
`PA{n}R` would find an unexpected `OKP{a}P{b}` waiting in the buffer. The
driver's `_drain()` already handles exactly that (§4).

### How to run the bench session

```
python3 tools/lkv422_probe.py --port /dev/hdmi-matrix
```

It records the current routing, switches to a different input, records whatever comes back, confirms with `PAXXR`, restores the routing it found, and prints a summary of the terminator and acknowledgement behaviour observed. Full timings are written to a `tools/lkv422_probe_<timestamp>.log` file (gitignored). Update §7.1 and §7.2 above with the result.

## A stray NUL after power-up (1 Oct 2026)

After the CM5 and the matrix were power-cycled together (moving into the
rack), the first poll logged `unexpected reply to PAXXR: b' '`. A lone
`0x00` can arrive on the line after the pre-request drain, probably as the
FTDI adapter or the matrix's UART comes up. The driver (`_read_reply`) now
discards leading NUL bytes before parsing. A lone NUL reads as "no reply",
and NULs followed by a malformed reply still read as "unexpected reply".
